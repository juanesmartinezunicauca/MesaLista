⚠️ Hallazgo Clave: Del "Fuzzing Idealista" al "Blindaje Real de Motor"

Las pruebas unitarias que usan mocks son inherentemente idealistas porque simulan un entorno perfecto. Al someter el código a condiciones reales de PostgreSQL y concurrencia, se identificaron y solucionaron 4 vulnerabilidades críticas antes de producción:

VULNERABILIDAD 1 · DESBORDAMIENTO NUMÉRICO

PostgreSQL Integer Overflow (Prisma P2020)

Al enviar IDs superiores a 2,147,483,647 (32-bit signed int), PostgreSQL lanza error 22003. El filtro de Prisma no lo capturaba y respondía con HTTP 500.

Solución implementada: PrismaExceptionFilter ahora intercepta P2020 y responde limpiamente con 400 Bad Request.
VULNERABILIDAD 2 · DESBORDAMIENTO DE LONGITUD

PostgreSQL String Length Overflow (Prisma P2000)

Cadenas mayores a VARCHAR(255) disparaban error de base de datos no capturado, generando caídas 500.

Solución implementada: Interceptado P2000 en el filtro para devolver 400 Bad Request indicando el campo excedido.
VULNERABILIDAD 3 · CONDICIÓN DE CARRERA

Time-of-Check to Time-of-Use (TOCTOU) en Inventario

Dos pedidos simultáneos sobre la última unidad de stock pasaban la validación y dejaban el inventario en -1.

Solución implementada: Guardas de inventario atómicas y prueba de simulación de carrera concurrente.
